<objective>
Fix three confirmed false-positive sources in the immunogen scanner that were inflating a real-world scan to an undeserved 0/100 "F", while preserving every true positive (real leaked secrets must still be caught at the same severity).

Root causes (already diagnosed by reading the source — no further investigation needed):

1. **Vendored iOS/macOS CocoaPods (`Pods/`) treated as scannable source.** `HARD_EXCLUDE_DIRS` in `src/core/ingest/file-walker.ts` already hard-excludes `node_modules`, `.next`, `dist`, `build`, etc. as vendored/generated noise, but `Pods` (CocoaPods' vendored-dependency directory — never code the developer authored, exactly analogous to `node_modules`) is missing from that list, so vendored library READMEs inside it produce false "high" findings.

2. **The SEC-04 Supabase service_role "env-name" signal fires on safe reads, not just leaks.** In `src/detectors/secrets/entropy-detector.ts`, `runSupabaseServiceRolePass` has two signals: (a) decode a JWT and check for `role: service_role` (precise, keep as-is), and (b) flag ANY line merely containing the substring `SUPABASE_SERVICE_ROLE_KEY` — with zero context check. Reading the var server-side via `Deno.env.get("SUPABASE_SERVICE_ROLE_KEY")` or `process.env.SUPABASE_SERVICE_ROLE_KEY` is the *correct, secure* pattern (Supabase Edge Functions doc-recommended), not a leak — but signal (b) flags it anyway, producing false "critical" findings. The real leak shape this signal exists for is a `KEY=value` assignment in a committed `.env` file (e.g. `SUPABASE_SERVICE_ROLE_KEY=eyJ...`), which is NOT an env-accessor call and must keep firing.

3. **The keyword-anchored entropy pass (SEC-06, Pass B) has no per-file cap, so one generated data file can flood the report with thousands of near-duplicate findings.** A generated JSON data dump (e.g. a code-graph export with many node objects shaped like `{"key": "<long random-looking id>", ...}`) legitimately matches the documented FP-management pattern (anchor keyword "key" + high-entropy quoted literal ≥40 chars on the same line, per `.planning/research/FEATURES.md` CAT-1 SEC-06) on every single node object — thousands of times in one file. This is a real gap other secret scanners handle by capping findings-per-file: past a small threshold, repeated identical-shaped matches in ONE file are far more likely to be a data/schema artifact than distinct secrets, and continuing to emit one Finding per match provides no additional signal while destroying the report's usability and the Ship Score. Provider-key regex (Pass A) and the Supabase JWT/env-name signal (Pass A2) are NOT subject to this cap — those are precision-anchored and every match is independently meaningful.

Fix all three without weakening true-positive detection: a single real secret (Stripe/AWS/OpenAI key, Supabase service_role JWT or hardcoded `.env` assignment) must still be caught exactly as before.
</objective>

function runSupabaseServiceRolePass(
  line: string,
  lineNumber: number,
  filePath: string,
  detectorName: string,
  findings: Finding[],
): Array<[number, number]> {
  const matchedSpans: Array<[number, number]> = [];

  for (const match of line.matchAll(JWT_RE)) {
    const matchedValue = match[0];
    if (!decodesToServiceRole(matchedValue)) {
      continue;
    }
    const start = match.index;
    matchedSpans.push([start, start + matchedValue.length]);

    findings.push({
      ruleId: SUPABASE_SERVICE_ROLE_RULE_ID,
      category: "secrets",
      detectorName,
      file: filePath,
      line: lineNumber,
      severity: "CRITICAL",
      confidence: "HIGH",
      message: "Hardcoded Supabase service_role JWT found in source.",
      remediation: "...",
      matchedText: maskSecret(matchedValue),
    });
  }

  for (const match of line.matchAll(SUPABASE_ENV_NAME_RE)) {
    const matchedValue = match[0];
    const start = match.index;
    matchedSpans.push([start, start + matchedValue.length]);

    findings.push({
      ruleId: SUPABASE_SERVICE_ROLE_RULE_ID,
      category: "secrets",
      detectorName,
      file: filePath,
      line: lineNumber,
      severity: "CRITICAL",
      confidence: "HIGH",
      message: "Reference to SUPABASE_SERVICE_ROLE_KEY found in source.",
      remediation: "...",
      matchedText: maskSecret(matchedValue),
    });
  }

  return matchedSpans;
}
